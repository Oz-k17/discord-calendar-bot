# ラボの作業記録

毎日 1 回のセッションがここを読んでから作業し、終わったら追記します。
**セッションは毎回まっさらな状態で始まる**ので、前の日に何をやってどう思ったかは
ここに書いてある内容がすべてです。

## 書き方

- 新しい日付は**いちばん上**に足す（最新が先頭）。
- 「やったこと」は 3 行以内。長い説明は各試作の README に書き、ここからは参照するだけ。
- **やってみて分かったこと・うまくいかなかったこと**を必ず 1 行は残す。
  次の日の自分にとっていちばん価値があるのはそこです。
- 途中で止めたものは「積み残し」に書いて、次の日が拾えるようにする。

## やることの候補

順番は決まっていません。その日に「これがいちばん効きそう」と思ったものを 1 つ選びます。
新しく思いついたものはここに足してください。逆に、やってみて筋が悪いと分かったものは
理由を書いて消してください。

### 音まわり（`auto-cut` の続き）

- **音楽が乗った素材でも声だけを見分ける** — いまのしきい値方式の最大の弱点。
  BGM 込みで録った素材だと全編が「鳴っている」判定になる。
  ゼロ交差率や帯域ごとのエネルギーで、音楽と声をある程度は分けられるはず。
- **長尺への対応** — `decodeAudioData` は素材全体をメモリに載せるので、
  10 分を超える素材で破綻する可能性が高い。まず実測してから考える。
- **ラウドネス正規化（LUFS）** — SNS の再生音量に合わせて -14 LUFS へ揃える。
  書き出しの最後に 1 回かけるだけなので、実装は軽いわりに効果が大きい。
- **クリップごとの音量の自動合わせ** — 複数のカットで声の大きさがバラバラなのを揃える。
- **ビート検出（BPM）** — 曲に合わせてカットを置きたいときの下地。
  タイムラインのスナップ先にビートを足せると強い。

### 映像まわり

- **シーン検出** — 素材の中でカットが切り替わっている場所を見つけて、自動で分割する。
  隣り合うフレームの差分を見るだけなので、考え方は無音カットとほぼ同じ。
- **被写体を追う自動リフレーム** — 横型素材から縦型を切り出すとき、
  人物や動きのある場所を追いかけてクロップ枠を動かす。本体のクロップの真上に乗る。
- **サムネイル候補の自動抽出** — ブレていない・情報量の多いコマを何枚か出す。
- **キーフレーム（時間で変化する値）** — 拡大・位置・不透明度を時間で動かす。
  本体のモデルに手が入るので、まずラボで「値の持ち方」を試したい。

### 書き出し・その他

- **書き出しの速度を測る** — いまは 1 コマずつなので遅い。どこで時間を使っているかを
  実測して、詰められるところを探す。
- **プロジェクトの持ち出し / 取り込み** — 素材ごと 1 ファイルにまとめて、
  別の端末で開けるようにする。

## 記録

### 2026-09-06 — ラボを作り、無音カットとオートダッキングを試作

- `lab/` を作成。本体のビルドからは完全に切り離してある。
- `lab/auto-cut` に、20ms ごとの音量の列を共通の材料として
  **無音カット（ジェットカット）・オートダッキング・波形表示**の 3 つを実装。
- コマンドラインから走るセルフテスト 20 件（`npm run lab:test`）。ブラウザもサーバも要らない。

**分かったこと**

- しきい値を固定値（-40dB など）にすると、録音レベルの違う素材でまったく効かない。
  素材ごとの音量の分布（下位 10% を無音の底、上位 10% を声）から決めるようにしたら、
  合成素材で自動的に -46.7dB が選ばれて素直に効いた。
- パラメータは 3 つ（感度 / 短い無音は残す / 前後の余白）で足りる。
  それ以上出すと、どれを触ればいいか分からなくなる。
- 判断する関数を DOM から切り離しておくと、Node が `.ts` をそのまま実行できるので
  テストがブラウザ無しで回る。ここは以降も守る価値がある。

**積み残し**

- 音楽が乗った素材では使えない（上の候補の 1 つ目）。
- 長尺での処理時間・メモリはまったく測っていない。
