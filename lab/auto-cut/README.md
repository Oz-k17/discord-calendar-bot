# 無音カット & オートダッキング（試作）

ViViD Edit に次に必要になりそうな機能として、**音を見て自動で編集する**ひとまとまりを試作しました。

```
npm run lab           →  画面を開く（http://localhost:5173/）
npm run lab:test      →  計算の検算（合成波形・ブラウザ不要・数秒）
npm run lab:fixtures  →  試し用の音を作る（lab/fixtures/out/）
npm run lab:probe     →  「どの特徴量なら声を見分けられるか」を正解付きで測る
npm run lab:bench     →  その素材で「実際どれくらい効くか」を測る
npm run lab:uitest    →  画面まで通して確かめる（playwright が無ければ飛ばす）
```

`lab:test` は「壊れていないか」、`lab:bench` は「どれくらい効くか」、
`lab:uitest` は「読み込む → 描く → 鳴らす、が繋がっているか」を見ます。役割が違うので 3 つとも要ります。

音声でも動画でも読み込めます（音だけを見ます）。読み込んだ素材はどこにも送信せず、
すべてブラウザの中で処理します。素材が無くても「3. セルフテスト」だけは実行できます。

---

## なぜこの機能か

いまの ViViD Edit は「切る・並べる・飾る」は一通りできますが、**どこを切るかは全部人が決める**作りです。
ショート動画づくりで実際にいちばん時間を取られるのはそこで、しかもその判断のほとんどは
「しゃべっていないところを詰める」という機械的な作業です。

そして、この判断に必要な材料（音量の時間変化）は、一度作れば別のことにも使い回せます。

| 機能 | 何が嬉しいか | 使う材料 |
| --- | --- | --- |
| **無音カット** | 尺を詰める作業が一瞬で終わる。今回の試作では 6.5 秒 → 4.0 秒（38% 削減） | 音量の列 |
| **オートダッキング** | 声の裏で BGM が自動で下がる。手で音量を書くより速く、しゃべりが埋もれない | 音量の列 |
| **波形表示** | タイムラインのクリップに波形が出ると、そもそも「どこを切るか」が目で分かる | 波形の山と谷 |

3 つとも入口が同じなので、まとめて作るのがいちばん安く付きます。

---

## 中身

判断する部分は DOM にも WebAudio にも依存していません。そのまま本体へ持っていけます。

| ファイル | 役割 |
| --- | --- |
| `src/loudness.ts` | 20ms ごとの音量（dBFS）の列を作る |
| `src/fft.ts` | スペクトルを取る（基数 2 の FFT）。依存を増やさないために自前で持っている |
| `src/features.ts` | 声らしさなど、コマごとの特徴量を並べる |
| `src/silence.ts` | しきい値を決め、残す区間と削る区間を出す |
| `src/ducking.ts` | 声の位置から、BGM に当てる音量カーブ（時刻と音量の並び）を出す |
| `src/peaks.ts` | 波形を描くための山と谷 |
| `src/edits.ts` | 計画（秒の並び）をタイムラインのクリップの並びに翻訳する |
| `src/selftest.ts` | 合成波形での検算。画面の「3. セルフテスト」と `npm run lab:test` の両方から呼ばれる |
| `selftest.mjs` | それをコマンドラインから走らせる入口 |
| `probe.mjs` | 正解の分かっている素材で、どの特徴量が効くかを測る |
| `bench.mjs` | 試し用の素材に対して、実際どれくらい効くかを測る |
| `uitest.mjs` | 画面まで通した確認（playwright を借りて動かす） |
| `src/demo.ts` `index.html` `src/style.css` | 見せる・鳴らすだけ。本体へは持っていかない |

### 無音カットの決め方

しきい値を「-40dB」のような固定値にすると、録音レベルが違う素材でまったく効かなくなります。
そこで**その素材の音量の分布**から決めています。

1. 下位 10% を「この素材の無音の底（部屋のノイズ）」、上位 10% を「声の大きさ」とみなす
2. その間を感度で内分してしきい値にする（既定 0.25 = 底寄り）
3. しきい値を超えたコマの前後に余白（既定 0.08 秒）を足す
4. 隣り合うものと、0.35 秒より短い切れ目しかないものを繋ぐ ← 息継ぎで切らないため
5. 残った短すぎる区間（0.15 秒未満）は捨てる ← 物音 1 発で 1 カットできるのを防ぐ

パラメータは 3 つだけ（感度 / 短い無音は残す / 前後の余白）で、
それぞれ「どういうときに動かすか」が画面に書いてあります。

### 声らしさの見分け方（`speech` モード）

音量だけでは、BGM や環境音が乗った素材で歯が立ちません。そこで「声らしさ」を別に測ります。

**どの手を使うかは、勘ではなく測って決めました。** 正解の分かっている素材
（どこでしゃべっているかを作る側が知っている）で、候補の特徴量それぞれについて
「声のコマとそれ以外を、どれくらい分けられるか」を AUC で並べたのが `npm run lab:probe` です。

| | きれいな声 | BGM 込み | ※ BGM 大 | ※ 打楽器 4Hz | 平均 |
| --- | --- | --- | --- | --- | --- |
| 音量（level） | 1.000 | 0.888 | 0.650 | 0.805 | 0.891 |
| 揺れの速さ（modulation） | 0.998 | 1.000 | **1.000** | 0.581 | 0.930 |
| 音色の尖り（tone） | 1.000 | 0.945 | 0.776 | **0.973** | 0.949 |
| 倍音らしさ（harmonicity） | 1.000 | 0.877 | 0.708 | 0.502 | 0.848 |
| **両者の積（speechScore）** | 1.000 | 1.000 | **1.000** | **0.841** | **0.974** |

読み方:

- **揺れの速さ**（音量が 1 秒に 3〜6 回上下しているか＝音節の速さ）は、BGM が大きい素材で完璧に効く。
  ただし **声と同じ速さで刻む打楽器には無力**（0.581）。これは狙って作った意地悪な素材で、
  「この手だけで行けそう」という思い込みを潰すために置いてある。
- **音色の尖り**（スペクトルが平坦でないか）は逆に、打楽器をきれいに弾くが BGM では鈍る。
- 互いの穴が重ならないので、**掛け合わせると最悪値がいちばん良くなる**（0.776 → 0.841）。
  平均だけを見て選ぶと `tone` 単体でも良さそうに見えるが、苦手な素材での落ち込みが違う。

しきい値（既定 0.20）も、正解付きの 4240 コマで取りこぼしと誤検出の釣り合いがいちばん良くなる
ところを探して決めました（声を 94% 拾い、声でないものを 6% 拾う）。

### オートダッキングの決め方

同じ音量の列から「声が鳴っている区間」を出し、そこだけ音量を下げるカーブを作ります。

- 下げ始めは声より **attack ぶん前**。声が出た瞬間にはもう下がりきっている
- 声が途切れても **hold** のあいだは戻さない（息継ぎのたびに戻ると落ち着かない）
- 戻すのは **release** の時間をかけて

返すのは `{時刻, 音量}` の並びなので、プレビュー（`GainNode`）でも
書き出し（`OfflineAudioContext`）でもそのまま同じものを流せます。

## 本体へ入れるとしたら

継ぎ目は少なく、既にあるものにそのまま乗ります。

**無音カット** — `src/model/ops.ts` の `splitAt` と `removeClips(ripple: true)` の組み合わせで表せます。
`edits.ts` の `toClipEdits()` が計画をその並びに変換するところまでやっているので、
あとは「選択中のクリップの音を `decodeAudioData` して計画を出し、その並びに置き換える」だけです。
UI はインスペクタに「無音をカット」ボタンと、プレビューで結果を確かめてから確定する形が合いそうです。

**オートダッキング** — 音量の上げ下げは既に GainNode で行っているので、そこへ流すだけです。

- プレビュー: `src/engine/audio.ts` の `setGain` の隣に、カーブを流す口を足す
- 書き出し: `src/engine/offline-export.ts` の `renderAudioMix()` にある `place(..., shape)` の
  `shape` が、まさに「音量の時間変化を組み立てる関数」なので、ここへ `applyDucking()` を渡す

**波形表示** — `peaks.ts` の結果をクリップの背景に描きます。
素材ごとに一度作って `mediaRegistry` に持たせておけば、タイムラインの描画は軽いままです。

## いまの実力（測った値）

`npm run lab:fixtures && npm run lab:bench` の結果です。素材は種を固定して生成しているので、
手を入れたあとに同じコマンドを叩けば、良くなったか悪くなったかがそのまま比べられます。

**削減率だけを見てはいけません。** 全部削れば削減 100% になりますが、それは声ごと消しているだけです。
「声をどれだけ残せたか」と「残したもののうち声だった割合」を並べて初めて、良くなったと言えます。

| 素材 | 削減（level → speech） | 声を残せた率 | 残したうち声だった率 |
| --- | --- | --- | --- |
| `speech.wav`（きれいな声） | 37% → 37% | 100% → 100% | 88% → 88% |
| `speech-quiet.wav`（録音レベル -18dB） | 37% → 37% | 100% → 100% | 88% → 88% |
| `speech-noisy.wav`（ノイズが大きい） | 38% → 38% | 100% → 100% | 89% → 89% |
| `speech-bgm.wav`（BGM 込み） | 27% → **38%** | 100% → 100% | 76% → **90%** |
| ※ `speech-bgm-loud.wav`（BGM が大きい） | **0% → 18%** | 100% → 100% | 55% → **67%** |
| ※ `speech-drums.wav`（4Hz の打楽器の上） | **0% → 44%** | 100% → **92%** | 55% → **91%** |
| ※ `drums.wav`（打楽器だけ・声なし） | 0% → 100% | — | — |
| `bgm.wav`（音楽だけ・声なし） | 0% → 80% | — | — |

読み取れること:

- **録音レベルが 18dB 違っても結果が変わらない**（`speech` と `speech-quiet` がどちらも 37%）。
  しきい値を素材ごとに決めている狙いは効いています。固定値ならどちらか一方は必ず外します。
- **音量だけでは歯が立たなかった 2 つ（※）が、切れるようになりました**（0% → 18% / 44%）。
- **きれいな素材では結果が変わりません**。効かない場面を助けるだけで、効いていた場面を壊していない。
- ただし `speech-drums` では **声を 8% 取りこぼしています**（100% → 92%）。ここは正直に残しています。
- 速度は `level` が 1ms 未満、`speech` が 130〜165ms（13 秒の素材）。
  音そのものを FFT にかけるぶん重くなりますが、10 分でも 6 秒程度の見込みです（未実測）。

## 分かっている限界

- **`speech` モードは声を少し取りこぼします**（打楽器の上で 8%）。
  谷を埋める窓を広げれば取りこぼしは減りますが、そのぶん切れ味が落ちます
  （窓 0.25 秒で取りこぼし 0%・削減 27%）。**声を切るのは取り返しがつかない**ので、
  既定は取りこぼさない側へ寄せてあります。
- **声の無い素材（音楽だけ）に `speech` を使うと、ほぼ全部削ります。** 契約上は正しい
  （残すべき声が無い）のですが、実用上は危険です。本体へ入れるなら、
  「声が 1 つも見つからなかった」ときは何もせず知らせる作りが要ります。
- **長尺は未確認**です。試したのは十数秒までで、`decodeAudioData` は素材全体を
  メモリに載せるので、10 分を超える素材では分割して読む工夫が要ると思われます。
  `npm run lab:fixtures -- long` で 10 分の素材が作れるので、まずそれで測るのがよさそうです。
- **試し用の素材は合成音です。** 本物の声・本物の音楽で同じように効くかは、まだ分かりません。
  意地悪な素材を足して思い込みは潰しましたが、それも自分で作ったものである以上、
  「自分の想定の外」は試せていません。
- **ダッキングは 1 対 1**（声 1 本 → BGM 1 本）しか見ていません。
  本体に入れるときは「どのトラックを声とみなすか」を選ばせる必要があります。
- 試作の再生はあくまで音だけです。映像と合わせた確認はしていません。
