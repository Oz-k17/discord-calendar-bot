# beat — 拍の検出（BPM とビートの位置）

曲のテンポを測り、**どの秒に拍が来るか**を並べます。
狙いは「曲に合わせてカットを置く」ことで、タイムラインの吸い付き先に拍を足せるようにする下地です。

```
npm run lab:beat            # 実際どれくらい効くかを測る（正解つき）
npm run lab:beat:probe      # どの手なら拍を見分けられるかを測る（実装する前に）
npm run lab:beats-fixtures  # 試し用の素材の一覧を出す
npm run lab:test            # 検算（ほかの試作のぶんと続けて走る）
```

| ファイル | 中身 |
| --- | --- |
| [`src/onset.ts`](./src/onset.ts) | 1 段目。「いつ音が立ち上がったか」の列を作る |
| [`src/tempo.ts`](./src/tempo.ts) | 2 段目。その列の繰り返しからテンポと拍の位置を出す |
| [`src/beats.ts`](./src/beats.ts) | 2 つを繋ぐ入口。使う側はここだけ見ればよい |

判断する部分は DOM にも WebAudio にも依存していないので、Node がそのまま `.ts` を実行できます。

## いまの効き（2026-09-21・2 回目・素材 18 本）

| | |
| --- | --- |
| BPM の当たり | **13/13**（倍・半分は外れに数えた） |
| 拍の F 値（±70ms） | **0.922**（16 本） |
| 当たった拍のずれ | 12.1ms |
| 「拍は無い」と言えた | 2/2 本 |

**判定は 1 回目から動いていません。** 数字が 0.968 → 0.922 に下がって見えるのは、
2 回目に**意地悪な素材を 3 本増やし、BPM の数え方を 1 つ直した**ためです。

- 足した素材: `tempo-change-120-90`（変わる向きを逆にした鏡）・
  `tempo-ramp-100-130`（段ではなく坂）・`break-116`（途中で打点が止まる）。
- 直した数え方: **テンポが一定でない素材を BPM の勘定から外した。**
  `tempo-change-90-120` の正解の中央値はたまたま 120 なので、
  後半にだけ合わせた手が「BPM は当たり・拍は 3 分の 1」で当たりに数えられていました。

同じ 18 本で 1 回目の作りを測ると同じ 0.922 です（既定は動いていません）。

## なぜこの作りなのか

### 立ち上がりの列を 2 本作る（テンポ用と位相用）

**テンポを当てる仕事と、拍の位置を当てる仕事は、欲しい列が違いました。**

| テンポに使う列 | 位相に使う列 | BPM の当たり | 拍の F 値 |
| --- | --- | --- | --- |
| energy | energy | 13/13 | 0.875 |
| **energy** | **flux** | **13/13** | **0.968** |
| energy | logFlux | 13/13 | 0.806 |
| flux | flux | 12/13 | 0.922 |
| logFlux | logFlux | 10/13 | 0.845 |

- **テンポに要るのは「列が周期的であること」。** 帯ごとに見る手（`logFlux`）は
  鳴っていない帯の微かな揺れまで同じ重さで数えるので、打点は拾えても**その間も埋まり**、
  周期が薄くなる。実際 `logFlux` は 13 本中 3 本で倍・半分に取る。
- **位相に要るのは「打点どうしの大きさの釣り合いが正しいこと」。**
  音量を dB（比）で見ると、**長く響く音の後ろに来た打点が前の音の尾に埋もれる**。
  `syncopated-128`（ウラのキックが強く、オモテのスネアが弱い）では、
  オモテの強さを **1.27 倍まで上げても位相が動かなかった**。
  そのまま（線形）のスペクトルで引き算に替えたら、同じ素材で拍が 0 本 → 34 本になった。

**1 段目の数字だけで列を選んでいたら、逆の手を掴んでいました。**
「拍の上にどれだけ集まるか」の平均は energy 3.03 / flux 3.10 / logFlux 2.92 で、
**打点を拾う力では `flux` のほうが上**です。それでもテンポでは負けます。

### テンポの重みは、素材の外から持ってきた仮定

自己相関のいちばん高い山をそのまま選ぶと、`hats-8th-120`（8 分ハットが拍より目立つ）で
半分の 60 と答え、`quiet-124` でも 62 と答えます（13 本中 11 本）。
中心 120BPM・幅 0.9 オクターブの釣鐘形の重みを掛けると 13/13 になります。

この重みは**素材の中から出てくるものではありません。**「速すぎる／遅すぎるテンポを人は取らない」
という入力への仮定なので、`priorBpm` / `priorOctaves` で外から変えられるようにしてあります。
素材の中から出せないものは外から入れるしかない、というのは
2026-09-18（3 回目）に倍率の基準で確かめたのと同じ形です。

### 「拍は無い」の線は、尺で動く

拍がまったく無い雑音でも、**短い素材では高い山がたまたま立ちます。**

| 尺 | 雑音だけの最大 | 拍のある素材の最小 | この線 |
| --- | --- | --- | --- |
| 4 秒 | 2.59 | 3.64 | 2.80 |
| 8 秒 | 1.76 | 2.70 | 2.27 |
| 16 秒 | 1.48 | 2.23 | 1.90 |
| 96 秒 | 1.28 | — | 1.37 |

自己相関は遠い所ほど足す回数が減るので、短い素材では**繰り返しを数回しか見ていない**。
見た回数が少なければ、雑音でも揃って見えることがあります。
そこで線を `1 + (基準の値 - 1) × √(16 ÷ 尺)` として、見た回数の平方根で縮めています。

**最初は 1.8 の固定値で入れていて、検算に落とされました**（8 秒の雑音で 1.94 が出た）。
素材が 1 つの長さしか無いと、尺で動く量を固定値だと思い込みます。

### 拍を近くの山へ寄せる手は、測って捨てた

人が叩いた揺れやハネを拾えるはずだと思って入れましたが、F 値の平均は
寄せない **0.875** / 1/16 0.872 / 1/8 0.867 / 1/4 0.864 / 1/2 0.812 で、**寄せるほど下がります**
（この段は列 1 本のときの数字）。理由は 2 つありました。

- **揺れのほうが許容幅より小さい**（±18ms 対 ±70ms）。寄せなくても最初から当たっている。
- 寄せると**声のある素材で拍が偽の打点へ吸われる**（`speech-over-110` が 0.759 → 0.690）。

直したい相手が許容幅の中に収まっているとき、寄せる手は得が無く損だけがあります。
`snapToPeak` は残してありますが既定では切ってあります（許容幅を詰めたら話が変わりうるため）。

### 途中で変わるテンポを追う — 作って、測って、既定にしなかった

2026-09-21（2 回目）の題材です。**窓ごとにテンポを出して繋ぐ**作りを入れましたが、
測った結果**既定では切ってあります**（`followTempo`）。

**1 段目（追えているか）は、よく当たりました。** 窓を 1 秒刻みで動かして
局所の正解と突き合わせたときの、ずれの中央値:

| 素材 | 窓 4s | 窓 5s | 窓 6s | 窓 8s |
| --- | --- | --- | --- | --- |
| 一定の素材（11 本） | 0.0〜0.5% | 0.0〜0.6% | 0.0〜0.6% | 0.0〜0.6% |
| `tempo-ramp-100-130`（坂） | 0.3% | 0.3% | 0.6% | 1.9% |
| `speech-over-110`（声が乗る） | 16.7% | 4.4% | 5.1% | 2.9% |

**2 段目（使えるか）で負けました。** その周期で実際に拍を並べたときの F 値:

| 素材 | 追わない | 窓 4s | 窓 5s | 窓 6s | 窓 8s |
| --- | --- | --- | --- | --- | --- |
| `tempo-ramp-100-130` | 0.508 | **1.000** | **1.000** | **1.000** | 0.852 |
| `tempo-change-90-120` | 0.667 | 0.561 | **1.000** | 0.561 | 0.561 |
| `tempo-change-120-90` | 0.667 | 0.607 | 0.607 | 0.596 | 0.596 |
| `pad-only-96` | 1.000 | 0.880 | 0.840 | 0.800 | 0.960 |
| `speech-over-110` | 0.966 | 0.345 | 0.690 | 0.230 | 0.733 |
| `break-116` | 1.000 | 0.968 | 0.968 | 0.968 | 0.968 |
| **平均（16 本）** | **0.922** | 0.895 | **0.941** | 0.882 | 0.915 |

**窓の長さを 1 つ変えるだけで平均が跳ねます。** こういう並び方は
「その長さに効いた」ではなく「その長さで 1 本が裏返った」を疑うところです。
実際 5s の得はほぼ `tempo-change-90-120` が 0.667 → 1.000 に裏返ったぶんで、
**向きを逆にした鏡の素材（`tempo-change-120-90`）は 0.667 → 0.607 と、むしろ下がったまま**でした。
**鏡の素材をこの回に足していなければ、5s を「効いた」と読み違えていました。**

負ける理由は 2 つ測れました。

**(1) 周期の誤差は足し算で溜まる。** 窓ごとの周期は 0.1〜0.5% しか外していませんが、
30 拍ぶん足すとその 30 倍がそのまま秒のずれになります。入れた当初
`tempo-ramp-100-130` は**全拍が外れ**（F 値 0.000・ずれ 250ms）でした。
1 歩ごとに近くの立ち上がりへ引き戻す（`trackGain`）と溜まりは止まり 1.000 になりますが、
**一度半拍ずれると引き戻しの幅（拍の 1/8）では戻れません**（幅を 1/3 まで広げると
`tempo-change-120-90` は 0.607 → 0.929 に戻り、代わりにほかが落ちて平均は下がります）。

なお 2026-09-21（1 回目）に「寄せる手は損しかない」と書いて捨てた `snapToPeak` と、
この引き戻しは別物です。**あれは格子が流れない前提での話**でした（直したい揺れ ±18ms が
許容幅 ±70ms の中に収まっていたので、寄せる得が無かった）。流れる格子では相手が幅の外にいます。
**同じ手でも、土台が変われば釣り合いが逆を向きます。**

**(2) 変わり目の場所そのものが偏る。** 正解の変わり目は 8.00 秒ですが:

| 素材 | 窓 4s | 窓 5s | 窓 6s | 窓 8s |
| --- | --- | --- | --- | --- |
| `tempo-change-90-120`（速くなる） | 7.50s | 8.00s | 7.50s | 7.50s |
| `tempo-change-120-90`（遅くなる） | 8.50s | 9.00s | 9.50s | 9.50s |

**速くなる素材では早く、遅くなる素材では遅れて見えます。** 窓を 3 秒まで縮めても
遅れは 1 秒残ります。理由は素材の側にあって、**窓が変わり目をまたぐと、その窓は
「秒で多いほう」ではなく「打点の数で多いほう」を答える**からです。
速いテンポは同じ秒数でより多くの打点を出すので、変わり目はどちら向きでも速い側へ寄ります。
テンポの重み（`priorOctaves` を 0.9 → 2.0）でも自己相関の割り方（`acfNorm`）でも動きません。
**つまみの問題ではなく、窓で測ることそのものの性質です。**

作ったものは残してあります。**窓ごとのテンポそのものは当たっている**ので、
テンポの表示や「テンポが動いた」を知らせる用途ならこのままで足ります
（`detectBeats(audio, { followTempo: true }).tempoCurve`）。

## 残っている穴

- **テンポが途中で変わる素材**（`tempo-change-90-120` / `-120-90` とも F 値 0.667）。
  上のとおり窓ごとに追う手は測って既定にしませんでした。
  **次に試すなら、窓を動かすのではなく「拍ごとに周期も一緒に選ぶ」形**
  （1 本の格子を先に決めてから位置を合わせるのではなく、
  1 拍ずつ「次はどこか」を選んでいく作り）。窓の長さという 1 つのつまみが
  「変わり目の鋭さ」と「手がかりの薄い所での迷子」を同時に決めてしまう問題は、
  窓を使わない形にしないと外れません。
- **素材の頭と尻に、鳴っていない所の拍が立つ**（`kick-120`・F 値 0.969）。
  格子は素材の端まで伸びるので、音が始まる前にも拍が 1 本出ます。
  吸い付き先としては無害なので、線を増やすより放ってあります。
- **`pad-only-96` のずれが 43.8ms** と大きい。打点が無く和音が変わるだけなので、
  立ち上がりが鈍く、山の位置が後ろへ寄ります。当たってはいます（許容幅 70ms の中）。
- **画面が無い。** 計算と測る段だけで、読み込む → 描く → 拍を出す、を通していません。
  `scene-cut` と同じ積み残しが 2 つ並んでいます。
- **`break-116` の余裕は 1 秒しかない。** 窓 5 秒に対してブレイクが 4 秒なので、
  窓の端が 1 秒ぶんだけ打点に掛かって助かっています。
  5 秒より長いブレイクのある素材では、追う側にすると破れます。

## 素材

`lab/fixtures/beats.mjs` に正解、`make-beats.mjs` が音を作ります（ファイルには書き出しません）。
**正解は「拍の秒の並び」で持ち、BPM はそこから出しています。** BPM だけを正解にすると、
テンポは当たっているのに拍が裏に乗っている手を「当たり」と数えてしまうためです。

**音は正解の拍の列そのものから鳴らしています。** BPM から計算し直すのではないので、
テンポが動く素材でも揺れる素材でも、正解と音がずれようがありません。

`※` は意地悪な素材です。向きは 5 つあります。

- **テンポを取り違えさせる**（`hats-8th-120`・`slow-72`）
- **拍の位置をずらさせる**（`syncopated-128`・`swing-104`・`jitter-118`）
- **そもそも拍が無い / 見えない**（`pad-only-96`・`noise-only`・`near-silence`）
- **テンポが一定でない**（`tempo-change-90-120`・`tempo-change-120-90`・`tempo-ramp-100-130`）
- **途中で手がかりが消える**（`break-116`＝6〜10 秒は打点が止まる。和音は鳴り続ける）

`tempo-change-120-90` は `tempo-change-90-120` の**鏡**として足した素材です。
**片方だけで測っていたら、窓 5 秒を「効いた」と読み違えていました。**
意地悪な素材は「難しくする」ためだけでなく、**自分の当たりが本物かを確かめる**ためにも要ります。

`syncopated-128` は**正解の置き方を 2 度直した素材**です。最初は「オモテには何も鳴らない」形に
しましたが、それではオモテを拍と呼ぶ根拠が素材の中に無く、外したのは判定ではなく正解のほうでした。
経緯は `beats.mjs` のその素材の注に書いてあります。

## 使う側から見た入口

```ts
import { detectBeats, snapToBeat, subdivide } from './src/beats.ts';

const { bpm, beats } = detectBeats(audioBuffer);
if (bpm != null) {
  const targets = subdivide(beats, 2);      // 8 分の位置も吸い付き先にする
  const at = snapToBeat(cutTime, targets);  // 近ければ拍へ寄せる、遠ければそのまま
}
```

`bpm` が `null` なら拍は見つかっていません。**そのときは黙って引っ込むのが正しい**ので、
呼ぶ側で適当な既定値（120 など）を埋めないでください。
