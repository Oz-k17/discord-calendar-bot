# export-cost — 書き出しの費用（どこで時間を使っているか）

書き出し（`src/engine/offline-export.ts`）は 1 コマずつ
「デコードを待つ → 描く → エンコードを待つ」を回している。遅いのは分かっていたが、
**どこが遅いのかは測られていなかった**ので、まずそこを測るための試作。

触る画面は無い。出口は 2 つのコマンドだけ。

```
npm run lab:test     # 数え上げ・重ねる待ち行列の検算（ブラウザ不要・数秒）
npm run lab:export   # 実測（ブラウザ・playwright が無ければ数え上げだけ出して終わる）

LAB_EX_DEPTHS=0,8,16 npm run lab:export   # 重ねる枚数を振る（0 は直列＝いまの本体）
```

## 2 段に分けてある

| | 何を見るか | 要るもの |
| --- | --- | --- |
| 数え上げ（`src/plan.ts`） | 何枚デコードするか・何回開き直すか・歩幅はいくつか | 何も要らない |
| 実測（`testkit/measure.ts`） | デコード・描画・エンコードに何ミリ秒かかるか | ブラウザ |

重ねる待ち行列（`src/pipeline.ts`）も時計にも DOM にも触らないので、
「何枚まで抱えるか・順番が狂わないか・失敗が消えないか」は `npm run lab:test` で回る。

**数えられるものを測るのは順番が逆**なので、先に数え上げを出してから、
残ったぶんだけをブラウザで測る。数え上げのほうは端末にも素材にも依らないので、
そのまま記録として持ち越せる。

## 測って分かったこと（2026-09-26・1024×576・390 コマ・5 回の中央値）

### 1. 遅いのはデコード。エンコードではない

| 段 | 合計 ms | 1 コマ ms | 取り分 |
| --- | ---: | ---: | ---: |
| decode | 2519 | 6.46 | **86.4%** |
| draw | 13 | 0.03 | 0.4% |
| encode | 384 | 0.98 | 13.2% |

壁時計 2.92s ＝ **実時間の 4.46 倍速**。

描く段が 0.4% しか無いのは、この試作が**素の 1 枚を貼るだけ**だから。
本物はテロップ・エフェクト・トランジションを重ねるのでここは増えるが、
**増えてもデコードの側は減らない**ので、下の話は変わらない。

### 2. 「取り分 86%」を「直せば 7.3 倍」と読んではいけない

直列を仮定した上限（`cost.ts` の `projectSpeedup`）では、
デコードをタダにすれば **7.34 倍**と出る。ところが実際にデコードを 2.9 倍速くしても、
**壁時計は 1.67 倍しか縮まなかった**。

| やり方 | 壁時計 s | decode ms | encode ms | 前と比べ |
| --- | ---: | ---: | ---: | ---: |
| `at-timestamps`（いまの本体） | 2.92 | 2519 | 384 | 1.00 倍 |
| `pool`（canvas を使い回す） | 2.43 | 1756 | 658 | 1.20 倍 |
| `sequential`（順に読む） | 1.90 | 1173 | 713 | 1.54 倍 |
| `sequential-pool`（両方） | 1.75 | 878 | 855 | **1.67 倍** |

デコードが 2519 → 878ms に落ちたぶん、**エンコードが 384 → 855ms に増えている**。
段ごとの時計が測っているのは「その段が重いか」ではなく
**「そこで待たされたか」**で、`videoSource.add()` はエンコーダが詰まっていれば返ってこない。
片方を速くすると待ちがもう片方へ移るだけなので、**直列を仮定した上限は当てにならない。**

### 3. 効くのは「順に読む」こと。ただし飛ばして読むときは逆に損

mediabunny の `CanvasSink` には 2 つの読み方があり、本体は飛び石のほう
（`canvasesAtTimestamps`）だけを使っている。docs には
「**順に読むなら `canvases()` のほうが良い**（先読みが効く）」と書いてある。

| 再生速度 | 歩幅（素材コマ） | 順に読む形 |
| ---: | ---: | ---: |
| 1 倍 | 0.5 | **1.80 倍** |
| 2 倍 | 1.0 | 1.30 倍 |
| 3 倍 | 1.5 | 1.05 倍 |
| 4 倍 | 2.0 | **0.83 倍（損）** |

飛ばして読むぶんには、要らないコマまで canvas へ起こす手間がそのまま無駄になる。
**「順に読むほうが速い」は、順に読むときだけの話だった。**

`src/plan.ts` の `decodeShape()` は、この歩幅を**時計を使わずに**出して
どちらの読み方が向くかを返す。線は互角だった 1.5 ではなく **1.25** に置いてある
（互角で乗り換えても得が無いこと、そして境目ちょうどに線を置くと
浮動小数の丸めが答えを決めることの 2 つ。後者は同じ日に一度踏んだ）。

### 4. 1 本の素材を割ると遅くなる。出来上がりは 1 ビットも変わらないのに

本体はデコーダを**クリップごと**に開く。1 本の動画を 20 個に割ったタイムラインでは、
同じファイルを 20 回開き直して、20 回鍵コマから読み直す。

| 割る本数 | やり方 | 壁時計 s | 開く回数 | 開く ms | decode ms |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1 本 | `at-timestamps` | 3.08 | 1 | 4 | 2502 |
| 5 本 | `at-timestamps` | 2.86 | 5 | 18 | 2543 |
| 20 本 | `at-timestamps` | 3.18 | 20 | 74 | 2931 |
| 20 本 | `shared`（素材ごとに 1 本） | 2.99 | 1 | 5 | 2305 |

**代価は「開く時間」には出ない。** 開く時間は 74ms（壁時計の 2%）でしかなく、
増えているのは**開いた直後のデコード**のほう（2502 → 2931ms）。
`開く ms` だけを見て「大したことない」と読むのが落とし穴で、
数え上げの `redundantOpens` が 19 と出ているのに実測が 1.03 倍しか動かないのも同じ理由。

### 5. 出口 — `auto`

3 つを、注文の形を見て組み合わせたのが `auto`。
**素材ごとに 1 本開き、canvas を使い回し、歩幅が狭ければ順に読む。**

| | `at-timestamps` | `auto` |
| --- | ---: | ---: |
| 1 本・等速 | 3.08s | **1.72s（1.79 倍）** |
| 20 本に割る | 3.18s | **1.82s（1.75 倍）** |
| 4 倍速 | 0.85s | **0.74s（1.15 倍）** |

4 倍速で `sequential-pool` が 0.83 倍と負ける場面でも、`auto` は 1.15 倍で通る。
**どちらが速いかを選べる形にしたので、潰し素材でも負けない。**

### 6. デコードとエンコードを重ねても、速くならなかった（2026-09-26・2 回目）

2. の「片方を速くすると待ちがもう片方へ移るだけ」から、**重ねれば両方ぶん縮むはず**と
書いて終わっていた。作って測ったら、**縮まなかった。**

`add()` が返す約束を `encodeDepth` 枚まで未完了のまま先へ進む形にしてある
（`src/pipeline.ts` の `InFlightQueue`）。0 枚がいまの本体と同じ直列。

| やり方 | 枚数 | 輪 s | 仕上げ s | 合計 s | decode ms | 投げ ms | 待ち ms | 振れ幅 | 前と比べ |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `at-timestamps` | 0 | 2.88 | 0.07 | 2.95 | 2185 | 622 | 64 | 3.7% | 1.00 倍 |
| `at-timestamps` | 1 | 2.67 | 0.03 | 2.70 | 2211 | 438 | 9 | 3.9% | 1.09 倍 |
| `at-timestamps` | 4 | 2.67 | 0.03 | 2.70 | 2155 | 497 | 10 | 3.1% | 1.09 倍 |
| `auto` | 0 | 2.06 | 0.06 | **2.12** | 813 | 624 | 615 | 2.9% | 1.39 倍 |
| `auto` | 1 | 1.52 | 0.58 | **2.11** | 824 | 621 | 71 | 10.4% | 1.40 倍 |
| `auto` | 2 | 1.58 | 0.55 | **2.13** | 795 | 733 | 42 | 2.1% | 1.38 倍 |
| `auto` | 4 | 1.59 | 0.48 | **2.06** | 937 | 632 | 10 | 9.3% | 1.43 倍 |

**出口にしたい `auto` の上では 1.00〜1.03 倍**、つまり何も起きていない（振れ幅 2〜10%）。
枚数を 8・16 まで増やしても合計 2.05〜2.21s で変わらない。
`at-timestamps` の側だけ 1.08〜1.09 倍と揃って出るが、そちらは 9/26（1 回目）の時点で
`auto` に置き換えるべきと分かっている形なので、**重ねる価値がある場所ではない。**

**既定は 0 枚（直列）のまま。** 道具としては残してあるので、
ハードウェアのエンコーダがある端末で測り直す価値はある（下の注を参照）。

#### なぜ縮まないのか — `encode` の取り分の半分以上は「待ち」ではなかった

| 読み方 | 倍率 |
| --- | ---: |
| `encode` の取り分をそのまま重ねる（素朴） | 1.76 倍 |
| **待っていた時間だけ**重なる | 1.41 倍 |
| 実測（いちばん良かった枚数） | **1.03 倍** |

`CanvasSource.add()` は、呼んだその場で `new VideoFrame(canvas)` を作り、
符号化器へ渡すところまでを**同期で**通す。待ちが入るのはその後ろだけ。
つまり `encode` の 1239ms（`auto`・0 枚）は **投げ 624ms ＋ 待ち 615ms** の 2 つで、
**約束を後ろへ回して消せるのは後者だけ**。前者は 1 ミリ秒も減らない。

`cost.ts` の `projectOverlap` は段の取り分をそのまま「重ねれば消える量」として扱うので、
**ここを 1.76 倍と読み違える。** 同じ日に `projectOverlapMs` を足して、
**重ねて消せるぶんだけ**を渡す形にした。それでも 1.41 倍と出て実測は 1.03 倍なので、
**見積もりは 2 段階に直してもまだ大きい。**

残りの説明は「消えた待ちが仕上げへ移っただけ」。`auto` の 1 枚は
輪が 2.06 → 1.52s へ縮むが、仕上げが 0.06 → 0.58s へ増えて**合計は動かない**。
符号化器は追い付いていないので、輪の中で払わなかったぶんを最後に払う。
**輪だけを見ていると「1.36 倍速くなった」と書いてしまう。**

#### 測り方: 交互に回さないと、振れ幅を差として読む

最初は他の節と同じく**設定ごとに固めて** 3 回ずつ測った。その表では
`auto` の 2 枚が **1.55 倍**と出ていた。**設定を交互に回したら 1.02 倍になった。**

固めて測ると、その間のページの温まり方・ほかのプロセス・ゴミ集めの波が
**そのまま設定の差に化ける**。1 回捨てても、ページごと 2 回空回ししても消えない
（どちらも「塊の中」を揃えるだけなので、塊どうしの差は残る）。
効きが 5% 前後のときは**塊を作らない**しかない。`bench.mjs` の `runInterleaved` が
1 周ごとに順番をひっくり返しながら回すのはそのため（先頭はいつも少し冷えているので、
行き帰りで打ち消す）。**この節だけ他と測り方が違うのは、この節だけ差が小さいから。**

#### 出来上がりの照合は、作り直した

重ねると絵が入れ替わる・順番が狂う・コマが落ちるのが怖い。ところが
**それまでの照合では捕まえられない**——`digests` は**エンコードへ渡す前の canvas** を
見ているので、その後ろで何が起きても同じ値が並ぶ。なので
**出来上がった WebM を読み直して**突き合わせる形を足した（`measure.ts` の `verify`）。

結果は**升目の開きの最大が 0.0000 / 255**、つまり 1・2・4 枚のどれでも
直列と**ビット単位で同じ**ものが出る。順番が狂わない理由は mediabunny の中を読んで
確かめてあるが（`src/pipeline.ts` の注）、**中を読んだ根拠と出口で測った根拠は別物**なので、
ここは後者を置いた。

**畳み方を 2 回間違えた。** 1 つ目は全コマを 1 つの平均にしたこと
（わざと 1 コマずらした相手が 0.71 / 255 で素通り）。2 つ目はコマごとに分けたあとも
**升目の平均**を見たことで、こちらも 3 / 195 コマしか立たない。
場面の中の動きは画面のごく一部なので、升目 256 個で割ると平均の中に消える。
**升目ごとの最大**で見ると 128 / 195 コマが立ち、canvas 側の指紋（129 / 195）とほぼ並ぶ。
**「検査を書いたらわざと壊して落ちることまで確かめる」を守ったから気づけた。**

## 数字を読むときの注意

- **ミリ秒そのものは持ち越せない。** 確認用のブラウザには GPU が無い
  （`browser.mjs` の swiftshader）ので、VP8/VP9 は丸ごとソフトウェアで回る。
  本物の端末にはハードウェアのエンコーダが付くので、**エンコードの側はもっと軽い**はず。
  その向きだと「デコードが支配する」はさらに強くなる。
- **1 回目は捨てる。** 同じ設定でも 1 回目だけ 1.8 倍遅い（1.97s 対 1.08s）。
  それも設定ごとに 1 回捨てるだけでは足りず、**ページ全体で 2 回空回し**してから入っている。
  入れる前は振れ幅が 75% あり、`pool` の効きが 1.68 倍に見えていた（実際は 1.23 倍）。
- **小さい絵では測れない。** 512×288 では 4 つのやり方が 1.17〜1.29 倍と団子になり、
  振れ幅（18〜30%）の中に埋まる。1024×576 なら振れ幅 7〜13% に対して
  1.00 / 1.20 / 1.54 / 1.67 と順に並ぶ。既定を `scale=8` にしてあるのはそのため。

## 本体へ持っていくとき

`src/plan.ts` の `decodeShape()` と `summarizePlan()` だけが要る部品で、
どちらも DOM にも WebCodecs にも触らない。`testkit/measure.ts` のほうは
**測るための作り**で、本体の輪の代わりにはならない（音もトランジションも入っていない）。

`src/pipeline.ts` の `InFlightQueue` も DOM にも WebCodecs にも触らないが、
**持っていく理由はいまのところ無い**（上の 6. のとおり効かなかった）。

まだ試していないこと:

- **`add()` の同期の手間（投げ 624ms・全体の 29%）を減らす。** 今回いちばんの収穫で、
  ここは**どの段の時計にも単独では出ていなかった**（`encode` の中に紛れていた）。
  中身は `new VideoFrame(canvas)`＝1024×576×4 バイトの複製を 390 回。
  canvas を経由しない渡し方（`VideoSampleSource` に自前の `VideoSample` を渡す、
  デコード結果をそのまま回す）があるなら、そちらのほうが筋がよさそう。
- **`poolSize` の枠の数。** 2 と 4 しか試していない。
- **本物の解像度（1920×1080）と、H.264 のハードウェアエンコーダ。** ここでは測れない。
- **音の側。** `renderAudioMix` は書き出しの前に全体を一括ミックスするので、
  尺に比例したメモリと時間を先払いしている。ここは 1 秒も測っていない。
- **ハードウェアのエンコーダがある端末で、重ねる形を測り直す。** ここでは
  デコードもエンコードもソフトウェアで同じ 4 芯を取り合っているので、
  重ねても取り合いに化けるだけという読み方ができる。エンコードが別の回路へ逃げる端末なら
  話が変わる可能性はある。**向きは分かるが桁は分からない**のは 9/26（1 回目）と同じ。
