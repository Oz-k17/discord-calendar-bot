# export-cost — 書き出しの費用（どこで時間を使っているか）

書き出し（`src/engine/offline-export.ts`）は 1 コマずつ
「デコードを待つ → 描く → エンコードを待つ」を回している。遅いのは分かっていたが、
**どこが遅いのかは測られていなかった**ので、まずそこを測るための試作。

触る画面は無い。出口は 2 つのコマンドだけ。

```
npm run lab:test     # 数え上げの検算（ブラウザ不要・数秒）
npm run lab:export   # 実測（ブラウザ・playwright が無ければ数え上げだけ出して終わる）
```

## 2 段に分けてある

| | 何を見るか | 要るもの |
| --- | --- | --- |
| 数え上げ（`src/plan.ts`） | 何枚デコードするか・何回開き直すか・歩幅はいくつか | 何も要らない |
| 実測（`testkit/measure.ts`） | デコード・描画・エンコードに何ミリ秒かかるか | ブラウザ |

**数えられるものを測るのは順番が逆**なので、先に数え上げを出してから、
残ったぶんだけをブラウザで測る。数え上げのほうは端末にも素材にも依らないので、
そのまま記録として持ち越せる。

## 測って分かったこと（2026-09-26・1024×576・390 コマ・5 回の中央値）

### 1. 遅いのはデコード。エンコードではない

| 段 | 合計 ms | 1 コマ ms | 取り分 |
| --- | ---: | ---: | ---: |
| decode | 2519 | 6.46 | **86.4%** |
| draw | 13 | 0.03 | 0.4% |
| encode | 384 | 0.98 | 13.2% |

壁時計 2.92s ＝ **実時間の 4.46 倍速**。

描く段が 0.4% しか無いのは、この試作が**素の 1 枚を貼るだけ**だから。
本物はテロップ・エフェクト・トランジションを重ねるのでここは増えるが、
**増えてもデコードの側は減らない**ので、下の話は変わらない。

### 2. 「取り分 86%」を「直せば 7.3 倍」と読んではいけない

直列を仮定した上限（`cost.ts` の `projectSpeedup`）では、
デコードをタダにすれば **7.34 倍**と出る。ところが実際にデコードを 2.9 倍速くしても、
**壁時計は 1.67 倍しか縮まなかった**。

| やり方 | 壁時計 s | decode ms | encode ms | 前と比べ |
| --- | ---: | ---: | ---: | ---: |
| `at-timestamps`（いまの本体） | 2.92 | 2519 | 384 | 1.00 倍 |
| `pool`（canvas を使い回す） | 2.43 | 1756 | 658 | 1.20 倍 |
| `sequential`（順に読む） | 1.90 | 1173 | 713 | 1.54 倍 |
| `sequential-pool`（両方） | 1.75 | 878 | 855 | **1.67 倍** |

デコードが 2519 → 878ms に落ちたぶん、**エンコードが 384 → 855ms に増えている**。
段ごとの時計が測っているのは「その段が重いか」ではなく
**「そこで待たされたか」**で、`videoSource.add()` はエンコーダが詰まっていれば返ってこない。
片方を速くすると待ちがもう片方へ移るだけなので、**直列を仮定した上限は当てにならない。**

### 3. 効くのは「順に読む」こと。ただし飛ばして読むときは逆に損

mediabunny の `CanvasSink` には 2 つの読み方があり、本体は飛び石のほう
（`canvasesAtTimestamps`）だけを使っている。docs には
「**順に読むなら `canvases()` のほうが良い**（先読みが効く）」と書いてある。

| 再生速度 | 歩幅（素材コマ） | 順に読む形 |
| ---: | ---: | ---: |
| 1 倍 | 0.5 | **1.80 倍** |
| 2 倍 | 1.0 | 1.30 倍 |
| 3 倍 | 1.5 | 1.05 倍 |
| 4 倍 | 2.0 | **0.83 倍（損）** |

飛ばして読むぶんには、要らないコマまで canvas へ起こす手間がそのまま無駄になる。
**「順に読むほうが速い」は、順に読むときだけの話だった。**

`src/plan.ts` の `decodeShape()` は、この歩幅を**時計を使わずに**出して
どちらの読み方が向くかを返す。線は互角だった 1.5 ではなく **1.25** に置いてある
（互角で乗り換えても得が無いこと、そして境目ちょうどに線を置くと
浮動小数の丸めが答えを決めることの 2 つ。後者は同じ日に一度踏んだ）。

### 4. 1 本の素材を割ると遅くなる。出来上がりは 1 ビットも変わらないのに

本体はデコーダを**クリップごと**に開く。1 本の動画を 20 個に割ったタイムラインでは、
同じファイルを 20 回開き直して、20 回鍵コマから読み直す。

| 割る本数 | やり方 | 壁時計 s | 開く回数 | 開く ms | decode ms |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1 本 | `at-timestamps` | 3.08 | 1 | 4 | 2502 |
| 5 本 | `at-timestamps` | 2.86 | 5 | 18 | 2543 |
| 20 本 | `at-timestamps` | 3.18 | 20 | 74 | 2931 |
| 20 本 | `shared`（素材ごとに 1 本） | 2.99 | 1 | 5 | 2305 |

**代価は「開く時間」には出ない。** 開く時間は 74ms（壁時計の 2%）でしかなく、
増えているのは**開いた直後のデコード**のほう（2502 → 2931ms）。
`開く ms` だけを見て「大したことない」と読むのが落とし穴で、
数え上げの `redundantOpens` が 19 と出ているのに実測が 1.03 倍しか動かないのも同じ理由。

### 5. 出口 — `auto`

3 つを、注文の形を見て組み合わせたのが `auto`。
**素材ごとに 1 本開き、canvas を使い回し、歩幅が狭ければ順に読む。**

| | `at-timestamps` | `auto` |
| --- | ---: | ---: |
| 1 本・等速 | 3.08s | **1.72s（1.79 倍）** |
| 20 本に割る | 3.18s | **1.82s（1.75 倍）** |
| 4 倍速 | 0.85s | **0.74s（1.15 倍）** |

4 倍速で `sequential-pool` が 0.83 倍と負ける場面でも、`auto` は 1.15 倍で通る。
**どちらが速いかを選べる形にしたので、潰し素材でも負けない。**

## 数字を読むときの注意

- **ミリ秒そのものは持ち越せない。** 確認用のブラウザには GPU が無い
  （`browser.mjs` の swiftshader）ので、VP8/VP9 は丸ごとソフトウェアで回る。
  本物の端末にはハードウェアのエンコーダが付くので、**エンコードの側はもっと軽い**はず。
  その向きだと「デコードが支配する」はさらに強くなる。
- **1 回目は捨てる。** 同じ設定でも 1 回目だけ 1.8 倍遅い（1.97s 対 1.08s）。
  それも設定ごとに 1 回捨てるだけでは足りず、**ページ全体で 2 回空回し**してから入っている。
  入れる前は振れ幅が 75% あり、`pool` の効きが 1.68 倍に見えていた（実際は 1.23 倍）。
- **小さい絵では測れない。** 512×288 では 4 つのやり方が 1.17〜1.29 倍と団子になり、
  振れ幅（18〜30%）の中に埋まる。1024×576 なら振れ幅 7〜13% に対して
  1.00 / 1.20 / 1.54 / 1.67 と順に並ぶ。既定を `scale=8` にしてあるのはそのため。

## 本体へ持っていくとき

`src/plan.ts` の `decodeShape()` と `summarizePlan()` だけが要る部品で、
どちらも DOM にも WebCodecs にも触らない。`testkit/measure.ts` のほうは
**測るための作り**で、本体の輪の代わりにはならない（音もトランジションも入っていない）。

まだ試していないこと:

- **デコードとエンコードを重ねる。** いまはどちらも `await` で直列に並んでいる。
  上の 2. のとおり待ちは移るだけなので、**重ねて初めて両方ぶん縮む**はず。
  ただし「1 コマずつ確実に」が壊れない作りにする必要がある。
- **`poolSize` の枠の数。** 2 と 4 しか試していない。
- **本物の解像度（1920×1080）と、H.264 のハードウェアエンコーダ。** ここでは測れない。
- **音の側。** `renderAudioMix` は書き出しの前に全体を一括ミックスするので、
  尺に比例したメモリと時間を先払いしている。ここは 1 秒も測っていない。
