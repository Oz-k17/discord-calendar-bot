# scene-cut — シーン検出

素材の中でカットが切り替わっている場所を見つけて、自動で分割するための試作。
2026-09-20（4 回目）に、**映像まわりでは最初の試作**として作った。

```
npm run lab:test                  # 計算の検算（合成したコマ・ブラウザ不要・数秒）
npm run lab:scene:probe           # どの量なら見分けられるか（正解付き。実装する前に）
npm run lab:scene                 # 実際どれくらい効くか（数字を記録に残す）
npm run lab:scene:portrait        # 同じものを縦型（9:16 の切り出し）で測る
npm run lab:scene:native          # 同じものを縦型（最初から縦で撮った）で測る
npm run lab:scene:probe:portrait  # 縦型で並べて比べる
npm run lab:scene:captions        # 全素材へ焼き込みの文字帯を乗せて測る（26%）
npm run lab:scene:caption-probe   # 帯の透け方が線の上下をどう動かすか測る
npm run lab:frames                # 試し用のコマを作って、一覧を出す
npm run lab:scene:demo            # 画面（本物の動画を読み込んで切り所を見る）
npm run lab:scene:uitest          # 画面まで通して確かめる（playwright が要る）
LAB_FPS=30 npm run lab:scene      # コマの速さを変えて測る（下の「コマの速さ」を参照）
LAB_CAPTIONS=0.4 npm run lab:scene # 文字帯の厚さを変えて測る（画面の高さの何割か）
LAB_CAPTION_ALPHA=0.5 npm run lab:scene # 帯の板を透かして測る（1 = 不透明・既定）
```

| ファイル | 役割 |
| --- | --- |
| `src/frames.ts` | コマを「くらべられる小さな形」に直す（縮小・ヒストグラム・距離）。判断は置かない |
| `src/scene.ts` | 距離の列から切り所を決める。DOM も canvas も要らない |
| `src/selftest.ts` | 計算の検算。素材は作らないので速い |
| `src/decode.ts` | 本物の動画 → コマの列。**判断はしないが、ブラウザが要る**（WebCodecs と canvas） |
| `src/demo.ts` / `index.html` | 画面。見せるだけで、判定は `scene.ts` を 1 回呼ぶだけ |
| `probe.mjs` / `bench.mjs` | 正解つきの素材で測る |
| `score.mjs` | 採点の物差し。`bench.mjs` と `uitest.mjs` が**同じものを呼ぶ** |
| `testkit/encode.ts` | 確かめ用に素材を本物の動画へ焼く。**画面には入っていない** |

入口は `ImageData` と同じ形（RGBA の並び）にしてある。本物の動画では
「デコードしたコマを小さな canvas へ描いて `getImageData()`」という経路になり、
そこは 2026-09-22（2 回目）に `src/decode.ts` として通した。
**そこから先は canvas も DOM も要らない**ので、測定はこれまでどおり Node のまま回る。
出てくる `scenes` は隙間なく並ぶので、`auto-cut/src/edits.ts` の `toClipEdits` へ
そのまま渡せば「1 本のクリップを場面ごとに割る」になる（検算で通してある）。

**3 つの向きとも、見つけた率 92.3% ／ 当てた率 98.0% ／ ずれの平均 0.010 秒**

| 選び方 | 横型 16:9 | 縦型（切り出し） | 縦型（最初から縦） |
| --- | --- | --- | --- |
| **`combined`（既定）** | **92.3% / 98.0%** | **92.3% / 98.0%** | **92.3% / 98.0%** |
| `lumaHist` だけ | 88.5% / 100.0% | 88.5% / 100.0% | 88.5% / 100.0% |
| `rgbHist` だけ | 88.5% / 95.8% | 88.5% / 95.8% | 88.5% / 95.8% |
| `grid`（画素の引き算・線 0.040） | 80.8% / 97.7% | 78.8% / 100.0% | 80.8% / 97.7% |
| またぐ門を外す（`LAB_NOGATE=1`） | 96.2% / 87.7% | 96.2% / 87.7% | 96.2% / 87.7% |
| その場と比べる線を外す（`LAB_LOCAL=off`） | 92.3% / **90.6%** | 90.4% / **71.2%** | 92.3% / **92.3%** |

**旧 16 本だけで数え直すと 91.8% / 97.8%** で、2026-09-22（2 回目）までの数字と 1 桁まで同じ。
素材が 4 本増えたので全体の率は直接は比べられない。

**その場と比べる線は、2026-09-22（3 回目）から横型でも効いている。**
以前は切り出しの縦型でしか働いていなかった（横型は外しても 97.8% のまま）が、
固定の線を 0.10 → 0.05 へ下げたぶん、`pan-reveal` と `tilt` が固定の線を通るようになり、
**比だけが止めている**（外すと空振り 4 本、比は 1.6〜2.1 倍で線 4 倍の下）。
**線を下げた代価は、もう一方の線への依存**。両方を同時に緩めないこと。

`grid` は線 0.10 のままだと 30% まで落ちる。あの線はヒストグラム用なので、
**比べるときは量ごとに線を取り直すこと**（0.030 にすると当てた率が 69.1% へ落ちる。
下の「線の余裕」を参照）。

## 分かったこと

### 画素の引き算は、カメラが動いただけで破れる

いちばん素直な手（縮小して引き算）は、**パンと本物のカットがほとんど重なる**。
15 本で測って、正解のコマの最小が 0.044、パンの最大が 0.039——**差は 1.1 倍**しかない。
実際、線を 0.040 から 0.030 へ下げるだけで当てた率が 97.4% → 69.1% へ落ちる。

明るさの分布どうしを比べると、**画面の中で物が動いても分布は動かない**ので、
同じ素材で 0.167 対 0.051 と 3.3 倍開く。被写体が横切る素材（`motion`）では
0.008 しか動かない。**「どこが変わったか」ではなく「何が写っているか」を見るほうが、
カメラの動きに強い。**

### ただし、その強さは素材の性質でもあった

最初に作った `pan` は、帯が巡る（画面から出ていった中身が逆側から戻ってくる）素材だった。
**出入りする中身が同じなら、分布は原理的に 1 ビットも動かない。**
そこで一度も戻らない帯の上をパンする `pan-reveal` を足したところ、
誤検出の上限が 0.006 → **0.051** に上がり、線の余裕は 4.8 倍から 3.3 倍へ縮んだ。

入ってくる中身の割合と分布の動きはほぼ釣り合う（コマあたり 6% 入れ替わって 0.051）が、
**釣り合いは速いほうで鈍る**（入ってくる景色が出ていく景色と似てくるため）:

| パンの速さ | コマあたり入れ替わる割合 | 分布の動き |
| --- | --- | --- |
| 0.45 画面/秒 | 3% | 0.029 |
| 0.90 画面/秒 | 6% | 0.051 |
| 1.80 画面/秒 | 12% | 0.066 |
| 2.70 画面/秒 | 18% | 0.088 |
| 3.60 画面/秒 | 24% | **0.107**（線を越える） |

つまり**毎秒 3.5 画面を超えるパン**（ほとんど振り回し）で初めて線に届く。
そこまでは持つが、**「パンに強い」は無条件ではない**。

### 縦型（9:16）にすると、パンが破れる

2026-09-22 に縦型で測った。**縦型は「同じ絵を縦長の受け皿に描き直す」のではなく、
横型の画面から横を切り出す**形で作ってある（本体で縦型が出てくる経路がそれなので）。
受け皿の縦横比だけ変えると同じ絵が横に潰れて入るだけで、分布は画素をどこで数えても
同じ数になる——**「縦型でも 1 本も動きませんでした」という当たり前の結果**しか出ない。

切り出すと、画面に写る横の範囲は **81/256 ≒ 0.316 倍**（16:9 の高さから 9:16 を切るので）。
そのぶん、パンも手ぶれも横切る被写体も**画面に対しては 3.16 倍の速さ・大きさ**で効く。
結果、`pan` の隣どうしの距離が **0.006 → 0.160** まで上がり、既定の線 0.10 を越える:

| 素材（カットは 1 つも無い） | 横型の最大 | 縦型の最大 |
| --- | --- | --- |
| `pan`（帯が巡る） | 0.006 | **0.160** |
| `pan-reveal`（戻らない） | 0.051 | 0.089 |
| `handheld` | 0.035 | 0.038 |
| `motion` | 0.008 | 0.024 |
| `zoom` | 0.009 | 0.012 |

横型で `pan` が 0.006 しか動かなかったのは、**画面が帯を丸ごと写していたから**だった。
窓が帯の 3 分の 1 しか見なくなると、巡る帯でも「新しい中身が入ってくる」ことになる。
2026-09-20 に `pan-reveal` を足して分かった「強さは素材の性質でもあった」が、
**向きを変えただけでもう一度出た**形。

### 線を上げる形では直らない。基準をその場から取り直す

縦型だけ見れば、線を 0.160〜0.426 のあいだに置けば通る。
**ところが横型のカットは最小 0.167** なので、1 本の固定線に残る余裕は **1.04 倍**しかない。
つまみの振り幅ではなく、**固定の線そのものが向きに耐えない。**

そこで見るのを大きさから「**その場のふだんの高さの何倍立っているか**」へ変えた
（`localRatio`）。パンは**ずっと同じくらい動き続ける**ので周りも高く、
カットは**1 コマだけ跳ねる**ので周りが低い。
音の側で `lowBandReadable` の線を「その場の低い側から 20dB 下」に取り直したのと同じ形で、
**固定の線が外れるときは、たいてい基準をその場から取り直すほうが効く。**

周りの代表値は**中央値**にしてある。平均だと、0.4 秒ごとに跳ねる `cuts-rapid` で
跳ねた側が周り側を引き上げ、**自分で自分を隠す**（検算に入れてある）。
自分の左右 1 コマを数えないのは、**渡りの縁は「周り」ではなく本人の一部**だから。

### その線を潰す素材も一緒に作った（`pan-cuts`）

「周りが静かなのに跳ねたか」を見る以上、**周りがずっと動いている所で本当に切り替わったら
見えなくなる**はず。パンしながらのカット（歩き撮りの繋ぎ）は実際によくある撮り方なので、
意地悪であると同時に本物の使い道でもある。狙いどおり破れた——入れた当初の線（20 倍）では
縦型で 2 本とも見逃し、見つけた率が 91.8% → 87.8% へ落ちた。

**線の上と下は、両方ともこの手を潰す素材が決めている:**

| | 比 | 何がそこにいるか |
| --- | --- | --- |
| 下限 | 2.8 倍 | `dark-noise`（暗所のノイズ） |
| **既定** | **4 倍** | |
| 上限 | 7.8 倍 | `pan-cuts`（パンしながらのカット） |

16 本で振ると **2〜7 のあいだは 1 本も動かない**。台の真ん中を取っている。

**窓の幅（`localWindow` = 30 コマ ＝ 2 秒）にも下限がある。** 狭いと**渡りが自分で自分を隠す**:
1 秒のディゾルブ（15 コマ）を W=8 で見ると窓の中がほとんど渡りで埋まり、
比が 1.1 倍まで落ちて**落ちてしまう**（W=15 で 43.5、W=30 で 56.9）。
フラッシュをまたぐ幅を「光っている長さより広く」取ったのと、同じ形の下限。
8 コマにすると両方の向きで見つけた率が 91.8% → 89.8% へ落ちる。15〜45 は動かない。

### 最初から縦で撮ると、パンは破れない。破れていたのは切り出しのほう

**2026-09-22（3 回目）に、横を切らない縦型（`native`）を足して分かった。**
9/22（1 回目）に「縦型ではパンが破れる」と測ったが、あれは
**9:16 を切り出したから**で、縦であることの性質ではなかった。

| 素材（カット 0 本） | 横型 16:9 | 縦型 9:16（切り出し） | 縦型 9:16（最初から縦） |
| --- | --- | --- | --- |
| `pan`（横に流れる） | 0.006 | **0.160** | 0.014 |
| `motion`（横切る被写体） | 0.008 | **0.024** | 0.013 |
| `crossing-vertical`（縦に動く被写体） | 0.016 | 0.012 | 0.009 |
| `tilt`（縦に流れる） | 0.056 | 0.062 | 0.056 |

**切り出しが増幅するのは横だけ。** 写る横の範囲が 0.316 倍になるので横の動きは 3.16 倍に効くが、
高さは切っていないので**縦の動きは 1 倍のまま**。実際 `crossing-vertical` は
切り出しても上がらない（0.016 → 0.012）のに、`motion`（横）は 3 倍になる。
最初から縦で撮った向きでは、どちらも横型とほぼ同じ値に戻る。

**受け皿を縦長にしただけでは、分布は 1 段も動かない**（検算で固定してある）。
画素をどこで数えてもヒストグラムは同じ数になるので、
`native` は**それ自体では何も測っていない対照**。動くのは素材の中身が縦向きのときだけで、
だから `tilt` と `crossing-vertical` を一緒に足している。
**「縦型で測る」と言うとき、切り出しなのか撮り方なのかを先に決めること。**
答えが逆になる。

### 焼き込みの文字帯は、線の上と下を同時に締める

短尺の動画には、字幕・見出し・アカウント名がほぼ必ず焼き込まれている。
**帯は場面が切り替わっても 1 画素も動かない**ので、分布の距離は動いた画素しか数えない以上、
**どのカットの距離もそのぶん薄まる**（`cuts-captions` は `cuts-plain` と同じ種・同じ切り所で、
帯だけが違う）。

**薄まる量は、帯の面積では決まらなかった。** 画面の 26% を覆う帯で予想は 0.74 倍だったが、
実測は切り所ごとに **0.85 / 0.72 / 0.73 倍**とばらつく。決めているのは面積ではなく
**帯が隠した中身**のほうで、空が変わるカットなら上の帯が面積以上に隠すし、
真ん中だけが変わるカットなら帯は何も隠さない（どちらも検算で固定した）。

締まるのは上だけではない。**同じ帯が、書き換わるときに小さな山を立てる**（`captions-only`）。
20 本で測った上下は、こうなる:

| 帯が覆う割合 | 本物のカットの最小 | 字幕の書き換えの最大 | 余裕 |
| --- | --- | --- | --- |
| 0%（帯なし） | 0.167 | 0.019 | 8.7 倍 |
| **26%（字幕＋見出し）** | **0.126** | **0.019** | **6.6 倍** |
| 40% | 0.078 | 0.030 | 2.6 倍 |
| 55% | 0.065 | 0.039 | 1.6 倍 |
| 70% | 0.049 | 0.049 | **1.0 倍**（線が引けない） |

**1 つの帯が、線を上からも下からも締めてくる。** 厚くすれば本物のカットは薄まり、
同じ厚みの帯が書き換わるときの山は逆に大きくなる。70% で交わって線が引けなくなる。

効きは既定（線 0.10 のまま）だとこうなった。26% では何も起きないが、40% から崩れる:

| 帯 | 線 0.10（もとの既定） | 線 0.05（いまの既定） |
| --- | --- | --- |
| 0% | 92.3% / 98.0% | 92.3% / 98.0% |
| 26% | 92.3% / 98.0% | 92.3% / 98.0% |
| 40% | **90.4%** / 97.9% | 92.3% / 98.0% |
| 55% | **88.5%** / 95.8% | 92.3% / 98.0% |
| 70% | **86.5%** / 100.0% | **90.4%** / 100.0% |

**この穴は比の線では塞げない。** 帯は距離の列を**まるごと**薄めるので、
比（`localRatio`）は約分されて動かない——つまり比は薄まりに強いが、**強すぎて気づかない**。
そして字幕の書き換えのほうは、比から見ると「周りが静かなのに跳ねた」そのものなので、
**比は 11〜15 倍まで立って止めない**。両方とも固定の線の仕事だった。

0.05 は上（本物の最小）と下（書き換えの山）の相乗平均にほぼ一致する
（帯 26% で √(0.019×0.126) = 0.049、帯 40% で √(0.030×0.078) = 0.048）。
**代価も書いておく。帯が無いときの余裕は 5.3 倍 → 2.6 倍へ減る。**
下げたことで固定の線を通るようになった候補は、測った限り**全部その場と比べる線が止めた**
（`pan-reveal` 1 本・`tilt` 5 本が `local` で落ちている）。

圧縮を通しても山は動かなかった（画面の確認で、同じ素材を WebM へ焼いて読んだ）:
書き換えの最大は合成コマ 0.019 → 焼いた動画 **0.021**、線 0.05 まで 2.4 倍ある。
9/22（2 回目）に「圧縮の粒は小さい距離ほど押し上げる」と測ってあるので、
**線を下げた以上ここは焼いて確かめないと意味がない**——確かめたうえで通っている。

### 透ける帯は、不透明な帯の「少しまし」な版ではない。壊れる側が逆になる

上の表はぜんぶ**不透明な板**の帯で測ったもの。実際の字幕はたいてい
**半透明の板に不透明な字**で置かれるので、2026-09-24 に透かして測り直した
（`npm run lab:scene:caption-probe`）。

**上（薄まり）はほとんど消える。** しかも面積のとおりには減らない:

| 板の不透明度 | `cuts-captions` の薄まり（3 つの切り所の平均） |
| --- | --- |
| 1（不透明） | 0.764 |
| 0.85 | 0.785 |
| 0.7 | 0.801 |
| 0.5 | 0.871 |
| 0 | 0.924 |

**板を 15% 透かしただけで、全面が変わるカットなら薄まりは丸ごと戻る**（検算で固定した）。
分布の距離が数えているのは**升目をまたいだ画素**であって、その画素がどれだけ動いたかではない。
カットで明るさが大きく変われば、15% に圧された変化でも升目はまたぐ。
——だから「帯は (1-k) 倍に薄める」は、**面積だけでなく透け方についても線形ではない。**

**下（書き換えの山）は逆に上がる。** しかも上がり方が偏っている:

| 板 | 1.5s | 3s | 4.5s | **6s** | 7.5s | 9s | 10.5s | 12s |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 不透明 | 0.0192 | 0.0188 | 0.0140 | **0.0016** | 0.0099 | 0.0102 | 0.0145 | 0.0061 |
| 0.5 | 0.0202 | 0.0229 | 0.0152 | **0.0109** | 0.0115 | 0.0097 | 0.0148 | 0.0123 |

動いているのは山ではなく**いちばん静かだったコマ**で、6 秒の書き換えは **6.7 倍**立つ。
理由は相殺だった。**板が不透明なら、点いた升目と消えた升目は「板の色」と「字の色」という
同じ 2 つの升目の間の出入りでしかない。** 同じ数だけ点いて消えれば分布は 1 段も動かない——
書き換えた画素がいくつであっても（帯の厚みを 12 / 26 / 50% と変えても 0 のまま。検算で固定した）。
板が透けると消えた側が下の絵の色へ散るので、相殺が解けて**動いた画素の数がそのまま出る**。

先に壊れる側が入れ替わる。既定（線 0.05）での効きはこうなった:

| 帯 | 不透明 | 板 0.85 | 板 0.5 | 板 0 |
| --- | --- | --- | --- | --- |
| 26%（実素材に近い厚み） | 92.3% / 98.0% | 92.3% / 98.0% | 92.3% / 98.0% | 92.3% / 98.0% |
| 40% | 92.3% / 98.0% | 92.3% / 98.0% | 92.3% / 98.0% | 92.3% / 98.0% |
| 55% | 92.3% / 98.0% | 92.3% / **96.0%** | **90.4%** / **92.2%** | 92.3% / **94.1%** |
| 70% | **90.4%** / 100.0% | **90.4%** / **94.0%** | **90.4%** / **88.7%** | 92.3% / **90.6%** |

（列ごとに板の不透明度を明示して測っている。`LAB_CAPTION_ALPHA` を渡さないと
`captions-only-sheer` だけが自前の 0.5 のままになり、列が混ざる。）

**不透明な帯は「見つけた率」から崩れ、透ける帯は「当てた率」から崩れる。**
不透明な帯を厚くしたときの壊れ方（本物のカットが薄まって見逃す）だけを覚えていると、
透ける帯では逆の症状——字幕の書き換えを切り所と読む空振り——が出る。
70% では当てた率が 100.0% → 88.7% と、**不透明なら 1 本も無かった空振りが 6 本**出る。

**既定は動かしていない。** 実素材に近い厚み（26%）では透け方をどう変えても数字が 1 つも動かず、
線 0.05 までの余裕も 上 3.1 倍 / 下 2.1 倍と残っている（不透明では 上 2.5 倍 / 下 2.6 倍）。
崩れるのは 55% 以上で、そこは不透明でも余裕 1.6 倍しかなかった所。
**線を下げる話が次に出たときに、この表の「下」を先に見ること。**

意地悪の素材としては、**厳しくなる側（`captions-only-sheer`）だけ**を一覧に足した。
透ける `cuts-captions` は距離が戻るぶん**易しくなるだけ**なので、並べても総合の数字が上がるだけで
壊れる所は増えない。

### フラッシュは、線では落とせない

カメラのフラッシュは分布を丸ごと動かすので、距離が 1.000 まで飽和する。
**線をどこに置いても、本物のカット（最小 0.167）より上に来る。**

落とせるのは、**変化をまたいで前後を比べた**ときだけ。カットなら「K コマ前」と
「K コマ後ろ」は別の場面のままだが、フラッシュなら同じ場面へ戻っている。

**またぐ幅は、落としたい変化の長さより広く取る必要がある。**
候補のコマは変化の真ん中とは限らず、端にも立つからで、5 コマぶん光るフラッシュを
K=5 でまたぐと「K コマ前」がまだ光の中に残る（誤りの最大 0.473）。
K=6 で 0.009 まで落ち、正解の最小 0.167 との間に線が引ける。

| またぐ幅 | 正解の最小 / 落としたい側の最大 |
| --- | --- |
| K=2〜4 | 0.15 / **1.000**（門が開いたまま） |
| K=5 | 0.15 / 0.473 |
| **K=6** | **0.17 / 0.014** |

**1 コマだけ飛ばす形（`d(i-1, i+1)`）では駄目だった。** フラッシュは立ち上がりと
降り際があり、**降り際は「大きく変わって戻らない」ので本物のカットと同じ顔をする**
（基準が光っている側になるため）。最初に測ったときの比は 2.0 前後で、カットと見分けが付かない。

### 門の代価は、短いインサート

またぐ幅より短い場面は、門が**丸ごとまたいで**前後に同じ絵を見つけてしまう。
0.33 秒のインサートが 2 回挟まる `quick-insert` では、候補は 4 本とも立つのに
門が 4 本とも落とす（見逃し 4 本）。門を外すと見つけた率は 91.8% → 95.9% へ上がるが、
**当てた率が 97.8% → 87.0% へ落ちる**ので、いまは門を入れたままにしてある。
（この釣り合いは向きで動かない——縦型でも同じ 95.9% / 87.0%。）

**これは釣り合いであって不具合ではない。** 同じ 0.4 秒という幅が、
片方ではフラッシュを落とし、もう片方では短いインサートを落とす。
`straddleFrames` を縮めればインサートは拾えるが、そのぶんフラッシュが通る。

### 門には、まだ塞げていない穴が 2 つある

**またぐ窓が本物のカットに届くと、そのすぐ手前のフラッシュが通る。**
門は「K コマ前と K コマ後ろが違うか」しか見ないので、後ろ側が本物の切り替わりに
届いてしまえば、間にあるのがフラッシュでも門は開く。検算に固定してある。

**門を通す順番で、連なりの中で残るコマが入れ替わる。**
まとめ（連なりから 1 本を残す）を門より後ろに置いたので、門が連なりの一部を落とすと
残るコマが変わる。「門は候補を減らすだけだから部分集合になる」と思い込んで書いた検算が、
その場で落ちて分かった。**順番をどちらにしても別の取り違えが出る**ので、
いまは「候補を 1 つずつ門にかけてからまとめる」側にして、振る舞いを検算で固定してある。
15 本での数字は、どちらの順番でも 1 本も動かない。

### 明るさの分布だけでは、色だけのカットが見えない

明るさを変えずに色だけが変わるカット（`cuts-samebright`）では、`lumaHist` は
**原理的に 0 しか返せない**（実測 0.011）。色の分布なら 0.886 で見える。

逆に、色の分布だけにすると黒へのフェードで山が縁からずれる（渡りの途中で最大になり、
黒の始まりと終わりを 0.43 秒外す）。**どちらも「見えないときは 0 に近い」側の外し方**なので、
足したり平均したりせず**大きいほうを取る**（`combined`）。

平均にしないのは、**見えているほうの値を見えないほうが薄めてしまう**から。
大きいほうを取る形なら誤検出の上限も 2 つの上限の大きいほうを超えないので、
**線の余裕を減らさずに取りこぼしだけを減らせる**（実測 87.2% → 91.5%）。

### 「渡りの真ん中」が無い渡りがある

ディゾルブ（1 秒かけて溶ける）は、渡りの真ん中に 1 点を置けば当たる。
**黒へ落ちて黒から上がるフェードは違った。** 黒が 1 秒続くあいだ絵は動かないので、
そこには**止まっている区間が 1 つある**——切り所は 2 つある。

最初は「渡り切る真ん中」を正解に置いていたが、測ったら検出は黒の両端
（5.87 と 7.00）を正しく見つけていて、真ん中では何も起きていなかった。
**正解の置き方のほうが間違っていた**ので、`scenes.mjs` の側を直してある。

いま残っている唯一の空振りも、同じフェードの中（5.47 秒）。
色の分布が渡りの途中で山を作るためで、黒の始まり（5.90）とは 0.43 秒離れているので
最短シーン長（0.4 秒）のまとめをすり抜ける。

### 線の余裕

`threshold` を **0.02〜0.14** で振っても、3 つの向きとも**結果は 1 本も動かない**
（文字帯の無い素材での話。帯があるときは下の節を参照）。
0.20 まで上げると横型の見つけた率が落ちる（切り出しの縦型は落ちない——
切り出したぶんカットの距離も大きくなるので、そちらのほうが線に余裕がある）。

**低い側の余裕は、その場と比べる線を入れてから広がった。**
入れる前は 0.02 まで下げると当てた率が 79.6% へ落ちていたが、いまは動かない。
小さすぎる変化を落とす仕事を固定の線が一手に引き受けていたのを、
**「周りより跳ねたか」の側が肩代わりしている**ことになる。

**ただし「だから固定の線は要らない」ではなかった**（2026-09-22・3 回目）。
その読みは、**字幕だけが書き換わる素材を持っていなかったから**成り立っていた。
書き換えは周りが静かな所で小さく跳ねるので、**比は 11〜15 倍まで立つ**（線は 4 倍）。
比の側から見ると本物のカットと同じ顔をしていて、止めているのは固定の線だけ。
既定を 0.10 → **0.05** へ下げたのは、その山（0.019〜0.049）を越えない範囲で
**帯に薄められたカットを拾える**のがそこだったから。下の節に測った数字がある。

### コマの速さ（fps）が、線の意味を決めていた

**2026-09-22（2 回目）に、本物の動画を読む前に測って分かった。**
既定のつまみは 15fps の素材で決めてあるが、本物の動画は 30〜60fps で来る。
同じ素材をコマの速さだけ変えて測ると、こうなる（`combined` の最大・`LAB_FPS`）:

| 素材 | 10fps | 15fps | 30fps | 60fps |
| --- | --- | --- | --- | --- |
| `cuts-plain`（瞬間のカット） | 0.976 | 0.976 | 0.976 | 0.976 |
| `quick-insert`（瞬間のカット） | 0.755 | 0.755 | 0.755 | 0.755 |
| `dissolve`（1 秒かけて渡る） | 0.303 | 0.243 | **0.149** | **0.086** |
| `fade-black`（黒へ落ちる） | 1.000 | 0.999 | 0.560 | 0.441 |

**瞬間の切り替わりは速さで 1 ミリも動かず、渡りだけが薄まる。**
渡りは「1 秒かけて起きること」なので、コマを細かく刻むほど 1 コマぶんの差が小さくなる。
ぜんたいの数字も動く（見つけた率 10fps 91.8% / 15fps 91.8% / 30fps **95.9%** / 60fps 93.9%）が、
中身は別の話が混ざっている——30fps で上がるのは**またぐ幅（6 コマ）が秒では半分になり**、
0.33 秒の `quick-insert` をまたげなくなって 2 本拾えるため。60fps ではディゾルブが
線を割って**丸ごと消える**。

**距離を「秒あたり」に直す手は使えない。** 割り算で直すと、今度は速さで動かないほう
（瞬間のカット）が速さに比例して動きだす。**2 つの量が逆向きなので、
割り算では両方を同時に固定できない。** 固定できるのは測る速さのほうだけなので、
`decode.ts` は素材が何 fps でも **15fps へ間引いてから**渡す。

これは 9/19 に音の側で出した答え（固定の線が外れるなら基準をその場から取り直す）とは
**逆向きの結論**で、ここでは基準ではなく**入力のほうを揃える**のが正しかった。
違いは「その場」が何かで、音の `lowBandRangeDb` は素材ごとに変わるものを追っていたが、
**コマの速さは素材の都合で、判定が追うべきものではない。**

### 圧縮の粒は、距離を押し上げる（小さい所ほど効く）

画面の確認（`uitest.mjs`）は素材を**本物の WebM に焼いてから**読むので、
合成コマをそのまま測るコマンドラインと数字を並べられる:

| 素材 @速さ | 合成コマ | 焼いた動画 | 切り所 |
| --- | --- | --- | --- |
| `cuts-plain` @60fps | 0.976 | 0.973 | 3 本 → 3 本（変わらず） |
| `fade-black` @60fps | 0.441 | **0.866** | 2 本 → 2 本 |
| `dissolve` @15fps | 0.243 | 0.354 | 1 本 → 1 本 |
| `dissolve` @30fps | 0.149 | 0.151 | 2 本 → 2 本 |
| `dissolve` @60fps | 0.086 | **0.136** | **0 本 → 2 本** |

**押し上げる向きにしか効かず、もともと 1.0 に近い所では効かない**（`cuts-plain` は動かない）。
量子化の粒が雑音の床として乗るので、**小さい値ほど比率で持ち上がる。**

ここから 2 つ言える。

- **ラボの数字は「きれいな入力での値」**であって、本物の動画では床が乗る。
  切りすぎる側（パン・手ぶれ・暗所ノイズ）の余裕は、実際にはここに書いた値より狭い。
- **60fps を間引かずに読んだときの壊れ方は、合成と本物で違う。**
  合成では線を割って消える（見逃し）が、本物では床のぶん線の上に残り、
  代わりに**渡りの中で 2 回立つ**（空振り）。どちらも「1 本」ではないので結論は同じだが、
  **「消える」とだけ書いていたら、本物を見たときに別の不具合だと思ったはず。**

## 画面（`npm run lab:scene:demo`）

2026-09-22（2 回目）に足した。動画を選ぶと、間引いて読んで、距離の列と切り所を描き、
割れた場面をサムネイルで並べる。**本物の動画のデコードを通しているのはここだけ。**

作りは拍の画面（`lab/beat/`）と同じ決め事にしてある。

- **画面で判定をやり直さない。** `planSceneCut` を呼ぶのは 1 か所だけで、
  描画も一覧も統計もその 1 回の結果を見る。だから `uitest.mjs` が
  「画面の切り所」と「コマンドラインの切り所」をそのまま突き合わせられる。
- **既定は判定の側から写す。** 画面に直書きすると黙って食い違う。
- **落とした候補も描く。** 見つけた所だけ描くと、切れなかったときに
  線が足りなかったのか門が閉じたのかが読めない。
- **縦の上端は「固定の線の 3 倍」で頭打ち。** 最初は素材の最大に合わせて伸ばしていたが、
  それだと本物のカット（0.9〜1.0）が上端を決めてしまい、**線の下で起きていること
  （パン 0.02・手ぶれ 0.005）が全部床に貼り付いて読めない。** 超えた柱には帽子を付けてある。

確かめ方（`npm run lab:scene:uitest`・26 件）で見ているのは、素材を**その場で WebM に焼いて**
画面へ食わせ、コマンドラインと当たり・見逃し・空振りを突き合わせるところ。
焼く部品（`testkit/`）は画面からは読み込んでいない。
音の側は WAV が無圧縮なので Node で書けたが、映像は焼く側も読む側も WebCodecs なので、
**ブラウザの中で焼く**形にした（新しい依存は増えていない。mediabunny は本体がすでに使っている）。

## 素材（`lab/fixtures/scenes.mjs`）

**ファイルには書き出していない。** 13 秒 × 15fps × 128×72 の RGBA で 1 本 7MB あり、
本物の動画にするにはエンコーダが要る（ラボに外部ライブラリは足さない方針）。
種を固定した生成なら毎回 1 ビットまで同じものが出るので、数字を並べる目的は満たせる。

意地悪の向きは 2 つ混ぜてある。片方だけ見ていると、
「切りすぎ」と「切らなさすぎ」のどちらかに倒れたことに気づけない。

| 素材 | 何のために |
| --- | --- |
| `cuts-plain` / `cuts-rapid` | 素直なカット。`cuts-rapid` は最短シーン長とちょうど同じ 0.4 秒間隔 |
| ※ `cuts-similar` | 同じ配色・同じ明るさのまま模様だけ変わる（見逃す側） |
| ※ `cuts-samebright` | **明るさの分布が 1 段も動かないカット**（既定の選び方を裏返して潰す） |
| ※ `dissolve` / `fade-black` | 渡りが瞬間ではない。正解の置き方そのものが論点 |
| ※ `pan` / `pan-reveal` / `zoom` / `handheld` / `motion` | カメラと被写体が動くだけ（切りすぎる側） |
| ※ `flash` / `flash-cuts` | 戻ってくる変化。線では落とせない |
| ※ `quick-insert` | **またぐ幅より短い場面**（門の代価を測るため） |
| ※ `pan-cuts` | **パンしながらのカット**（その場と比べる線を裏返して潰す） |
| ※ `tilt` / `crossing-vertical` | **縦に振る／縦に動く**（最初から縦で撮った素材の動き方） |
| ※ `cuts-captions` | **焼き込みの文字帯が乗ったままのカット**（距離が薄まる側） |
| ※ `captions-only` | **字幕だけが書き換わる**（切りすぎる側。固定の線の下限を決めている） |
| ※ `dark-noise` | 暗所のノイズ |

`cuts-captions` は `cuts-plain` と**同じ種・同じ切り所**で、違いは帯だけ。
薄まりがどれだけかを、引き算ではなく**並べて**読めるようにするため。

`cuts-rapid` を 0.4 秒間隔にしてあるのは、**最短シーン長とちょうど同じ値**を踏ませるため。
実際これで穴が 1 つ見つかった。引き算の丸め誤差だけで 31 本中 9 本が落ちていた
（いまはコマの半分ぶん甘くして通している）。

## まだやっていないこと

- **本物の動画で「測って」はいない。** 2026-09-22（2 回目）に読む所は通したが、
  正解の付いた本物の動画が手元に無いので、効きの数字はいまも合成コマのもの。
  焼き直した素材で分かるのは**圧縮の粒がどちらへ効くか**までで、
  手ぶれや圧縮の癖そのものは合成では作れていない。
- **格子（`grid`）は 32×18 のまま**で、縦型では升目が 2.25×7.1 画素の平たい形になる。
  既定の `combined` は画素をどこで数えても同じ分布なので影響を受けないが、
  `grid` と `changed` は縦の細かさだけ 3 倍ぶん先に均されている。
  いまの数字（縦型 77.6% / 100.0%）は横型（79.6% / 97.5%）と大きくは変わらないので、
  **測ったうえで直していない。**
- **縦型の「撮り方」はまだ 2 通りだけ**（2026-09-22・3 回目に `tilt` と
  `crossing-vertical` を足した）。手持ちの縦揺れ、縦に流れる被写体を追う動き、
  画面の端に寄った構図——縦型でよくあるものは、まだ並んでいない。
- **文字帯は「板と升目」でしかない。** 占める割合と動かなさだけを持たせた形なので、
  本物の字形・縁取りは入っていない。**半透明の板は 2026-09-24 に測った**（上の節）。
  残っているのは**縁取り**（字の周りだけ暗い輪郭）で、これは板と違って
  字と一緒に動くので、透け方の話とは別の相手になる。
- **`quick-insert` の 4 本**は落としたまま（門の代価として分かって落としている）。
- **`fade-black` の空振り 1 本**（5.47 秒）も残したまま。
- **門の穴 2 つ**（窓が本物のカットへ届く／順番でまとめの結果が変わる）は、
  塞ぐのではなく検算で固定しただけ。
