# thumbnail — 表紙（サムネイル）候補の自動抽出

尺の中から「表紙に使えそうなコマ」を何枚か出すための試作。
2026-09-23 に、**まだ一度も触っていない項目**として作った。

```
npm run lab:test            # 計算の検算（合成したコマ・ブラウザ不要・数秒）
npm run lab:thumb:probe     # どの量なら見分けられるか（正解付き。実装する前に）
npm run lab:thumb           # 実際どれくらい効くか（数字を記録に残す）
npm run lab:thumb:portrait  # 同じものを縦型（9:16 の切り出し）で測る
npm run lab:thumb:native    # 同じものを縦型（最初から縦で撮った）で測る
LAB_COUNT=5 npm run lab:thumb    # 何枚選ぶかを変える
LAB_SHARP=grad npm run lab:thumb # 細かさの測り方を変える（grad / cellRatio / cellMoving / gradNet）
LAB_NODIV=1 npm run lab:thumb    # 似た絵を避ける条件を外す（入れる前の振る舞い）

npm run lab:thumb:demo      # 画面（本物の動画を読んで候補を出し、絵として書き出す）
npm run lab:thumb:uitest    # 読む → 点を付ける → 候補を出す → 書き出す、が繋がっているか
```

| ファイル | 役割 |
| --- | --- |
| `src/thumb.ts` | コマ 1 枚を測る（細かさ・明るさ・黒つぶれ・粒・色）。**判断は置かない** |
| `src/pick.ts` | 点を付けて何枚か選ぶ。DOM も canvas も要らない |
| `src/selftest.ts` | 計算の検算。素材は作らないので速い |
| `src/export.ts` | 選んだ秒のコマを**素材の大きさで読み直して** PNG にする。判断は置かない |
| `src/demo.ts` / `index.html` | 画面。読む・見せる・書き出すだけ |
| `probe.mjs` / `bench.mjs` | 正解つきの素材で測る |
| `uitest.mjs` / `testkit/` | 画面を通して確かめる（素材をその場で WebM に焼いて食わせる） |
| `../fixtures/thumbs.mjs` | 素材と正解（**どの区間のコマなら使えるか**） |

入口は `ImageData` と同じ形（RGBA の並び）。本物の動画から取る経路は
`scene-cut/src/decode.ts` がそのまま使える（借りているのはそれと
`frames.ts` の分布の距離、`auto-cut/src/style.css` だけで、どれも判断をしない部品）。
同じものを 2 つ持つと、片方を直したときにもう片方が静かに古くなるため。

## いまの数字（`npm run lab:thumb` / 素材 10 本・3 枚ずつ）

| 向き | 駄目なコマを選んだ | 良い所から選べた | 場面の網羅 |
| --- | --- | --- | --- |
| **横型 16:9** | **0.0%** | **100.0%** | **100.0%** |
| **縦型（最初から縦）** | **0.0%** | **100.0%** | **100.0%** |
| 縦型（切り出し） | 6.7% | 55.6% | 100.0% |
| （比較）等間隔に選ぶ | 20.0% | 66.7% | 100.0% |
| （比較）頭から選ぶ | 30.0% | 0.0% | 33.3% |

- **駄目なコマ** … ボケている・黒い・白飛びしている・2 場面が重なって濁っている区間から選んだ割合
- **良い所から** … 「ここから選んでほしい」と正解に書いた区間から選べた割合
- **場面の網羅** … 3 枚が別々の場面から取れたか（4 場面ある素材で見る）

**削減率と同じで、片方だけを見ないこと。** 1 か所から 3 枚まとめて取れば
「駄目なコマ 0%」は簡単に出るが、それは表紙 3 枚ではなく同じ絵 3 枚。

## 決め方（測ってから決めたこと）

### 点 ＝ 細かさ × 写りの良さ × 周りと比べた明るさ

3 つとも掛け算。**どれか 1 つが駄目なら表紙にならない**ので、足し算にすると
真っ白なコマが「細かさが残っているから」で通ってしまう。

- **細かさ** … 隣り合う画素の差（`grad`）。手の込んだ 3 通りも測ったが、どれも負けた（下）
- **写りの良さ** … 明るさが 0.03〜0.97 の外で 0 へ落ち、飛んでいる画素の割合ぶん引く
- **周りと比べた明るさ** … 周り 0.8 秒の中央値の 1.1 倍までは満点、1.4 倍で 0 点

最後のものは、シーン検出で `localRatio` を足したときと同じ考え方。
**1 コマだけを見ても、白飛びと「もともと明るい絵」は区別が付かない**
（雪も逆光もふつうに明るい）。フラッシュが他と違うのは「周りが暗いのに自分だけ明るい」ことなので、
基準をその場から取る。外すと駄目なコマが 0.0% → 3.3% になる。

### 線は素材の外から引かない

細かさの高さは**素材ごとにまるで違う**（10 本で `grad` の中央値が 0.017〜0.036）。
「0.02 を超えたら鮮明」のような線を外から引くと、**文字帯の乗った素材では全コマが鮮明**になり、
**溶ける素材では全コマがボケ**になる。表紙は「どれを選ぶか」なので、
同じ素材の中での順位しか要らない。

### 似ていないことは、良いことの証拠ではない

**今回いちばん効いた直し。** 似た絵を避ける条件だけを置くと、
**いちばん壊れたコマがいちばん「似ていない」**ので、進んでそれを選ぶ。
静かな場面で 3 枚選ぼうとすると、ふつうのコマはどれも 1 枚目と似ているため全部飛ばされ、
**フラッシュで白く飛んだコマと、振り回してボケたコマだけが条件を通り抜けた**
（`flash` で 3 枚中 2 枚、`whip-still` で 1 枚）。
その素材のふつう（中央値）の 0.7 倍を下回るコマは、似ていなくても選ばないようにして塞いだ。

**似すぎの線は、中途半端に小さくすると外すより悪い**（0 で 0.0% のところ 0.08 で 6.7%）。
小さすぎる線は「似ていない絵」ではなく「少しだけ壊れた絵」を通すため。

### 足りないときに何を諦めるか

止まった場面では「似ていない 3 枚」は原理的に取れない。そのときは
**似すぎ → 時間の近さ → 出来** の順に諦める。点の高い順にそのまま埋めると、
隣り合うコマは点がほとんど同じなので **3 枚が 3 コマ続き**（0.07 秒ずつ）になる。
緩めた 1 枚には理由を付けて返すので、呼ぶ側は「3 枚とも同じくらい良い」と読まずに済む。

## 測って捨てたもの

- **升目ごとに比べる（`cellRatio`）** … 焼き込みの文字帯に乗っ取られないようにする狙い。
  良い所から選べた率が 100% → 88.9% へ落ちる。**もともと何も無い升目が「満点」を返す**ので、
  答えが薄まる。
- **動いた升目だけで測る（`cellMoving`）** … 帯は時間で動かないので外せるはず、という狙い。
  場面の網羅が 100% → 83.3%。場面が変われば升目はどこでも動くので、
  **外す相手が「動かない帯」ではなく「変化の少ない場面」になる。**
- **粒を引いた細かさ（`gradNet`）** … 「最初から縦」で駄目なコマが 0.0% → 26.7%。
  1 コマの中では**細かい肌理と粒ノイズが見分けられない**ので、引くと中身まで消える。
- **いちばん良いコマを基準にした下限（`floorBase: 'top'`）** …
  下限と場面の網羅がそのまま交換になる（0.6 で網羅 100%、0.9 で 33%）。
  素材の中でいちばん鮮明な場面が 1 つあると、ほかの場面が丸ごと線の下へ落ちる。

## 画面（2026-09-23・2 回目）

`npm run lab:thumb:demo`。本物の動画を読んで候補を出し、**選んだ絵を PNG で保存**する。
出口まで繋がったのはここが初めてで、`bench.mjs` は秒と点しか返していなかった。

### 読み込みが 2 本あるのは、間違いではない

**画面を作って初めて出てきた話。** 選ぶために読むコマと、書き出す絵は別物だった。

| | 大きさ | 速さ | 何コマ |
| --- | --- | --- | --- |
| 選ぶために読む（`scene-cut/src/decode.ts`） | 長辺 128 | 15fps に間引く | 尺ぜんぶ |
| 書き出すために読む（`src/export.ts`） | 素材のまま（長辺 1920 まで） | 選んだ秒だけ | 選んだ枚数 |

点の付け方は**素材の中での順位**で決まるので、選ぶほうは分布さえ残っていれば足りる。
ところが表紙は人が見る絵なので、**長辺 128 画素では使い物にならない。**
かといって全コマを大きいまま持つと、13 秒・195 コマの 1920×1080 で 1.6GB になる。
**選んだ数枚だけを、選んでから読み直す**形にした（リミッタを長尺へ当てるときと同じで、
要るのは「全部を持たない形」のほう）。

コマンドラインの測定は絵を出さないので、この 2 本目はずっと要らなかった。
**出口まで作らないと見えない穴がある**、の実例になっている。

### 画面で見せているもの

- コマごとの点を柱で、出来の下限を破線で、**飛ばしたコマを赤い柱で**描く。
  選んだ所だけ描くと「なぜそこが選ばれなかったか」（出来が足りないのか、似すぎたのか）が読めない
- 候補は絵で並べ、**条件を緩めて入れた 1 枚には理由を出す**
- 素材の大きさで読み直せたかどうかを毎回添える。
  **黙って 128 画素の絵を出すと、「この試作は 128 画素の表紙を出す」と読まれる**

### 確かめ方（`npm run lab:thumb:uitest`・25 件）

素材をその場で **WebM に焼いて**画面へ食わせる（`scene-cut` の `uitest.mjs` と同じ手）。
違うのは **4 倍に拡大して焼く**ことで、等倍だと素材が 128×72＝測るコマと同じ大きさになり、
**書き出しが素材の大きさで出ているのか、測ったコマを出しているのかが区別できない。**

いちばん確かめたいのは、この画面のいちばん静かな壊れ方——
**選んだ秒と書き出す秒が食い違う**こと。絵は出るし、大きさも合うし、点も出る。
違うのは「写っているもの」だけなので、数字のどこにも出ない。
書き出した PNG を測るときの大きさへ縮めてから、分布の隔たりで突き合わせている。

**この検査は、測る素材を間違えると素通りする。** 最初 `whip-still`（止まった場面）で
測っていて、自分と 0.0191 対 ほかの候補と 0.0194・0.0221 と**差が 2% しか出なかった**。
止まった場面では候補 3 枚がどれも同じ絵なので、**書き出しが別の候補とすり替わっても
分布が変わらない**——検査が「壊れていないこと」ではなく「壊れても同じに見えること」を
確かめていた。場面が 4 つ変わる `cuts-plain` へ移して、自分と 0.0176 対 ほかと 0.68・0.55（39 倍）。
**わざと入れ替えて FAIL することも確かめてある**（自分と 0.5582）。

## まだ出来ていないこと

- **縦型（9:16 の切り出し）で破れる**（駄目 6.7% / 良い所から 55.6%）。
  切り出すと中身が 1.8 倍に拡大されて眠くなるので、**ボケたコマと鮮明なコマの差が
  横型の 2 倍から 1.1〜1.6 倍まで縮む**。上の 4 通りを全部当てたが、どれも届かなかった。
- **3 枚まとめて落とす口が無い**（いまは 1 枚ずつ）。ブラウザの既定では
  まとめて落とすと 2 枚目以降が黙って止まる端末があるので、測ってから決める。
- 書き出しは PNG だけ。配信サイトの一覧は JPEG を求めることが多いので、
  どちらで出すかは置き先が決まってから。
- 「人が写っているか」「顔が写っているか」は一切見ていない。
  実際の表紙選びでいちばん効くのはたぶんそこだが、それは別の道具の話。
